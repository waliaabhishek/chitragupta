# Contributing to Chitragupta

## Commit Message Convention

```
<Type>: [TASK-NNN —] <short description>
```

**Types:**

| Type | Changelog section | When to use |
|------|-------------------|-------------|
| `Feat` | Added | New feature or capability |
| `Fix` | Fixed | Bug fix |
| `Docs` | Documentation* | Documentation-only changes |
| `Refactor` | Changed | Code restructure without behavior change |
| `Security` | Security | Security-relevant fixes |
| `Remove` | Removed | Removal of feature or API |
| `Chore` | *(omitted)* | Tooling, CI, dependency updates |

\* `Documentation` is a project-specific extension to Keep a Changelog's standard sections.
`Chore`, `Test`, and `CI` commits are omitted from the user-facing changelog.

Capitalize the type. `TASK-NNN —` is optional for non-task commits (hotfixes, tooling).

**Examples:**
```
Feat: TASK-110 — Add CSV export for chargeback reports
Fix: TASK-109 — Correct billing period boundary calculation
Docs: Update configuration reference for new metrics backend
Chore: Bump mkdocs-material to 9.6
```

## Documentation

Give each concept one canonical page. Other pages should include only the
details their audience needs and link to that page instead of repeating the
full feature narrative. Keep getting-started pages minimal, configuration
references focused on fields and validation, API references focused on HTTP
contracts, and operations pages focused on deployment and runtime actions.

## Changelog

`CHANGELOG.md` is generated by [git-cliff](https://git-cliff.org/).
**Do not edit `CHANGELOG.md` manually** — content is derived entirely from commit messages.

## Release Process

1. Ensure `main` is clean, current, and passing CI, and that all commits for the
   release use the type prefixes above.
2. Preview the release notes. For a stable release, compare with the previous
   stable tag so changes from ignored release-candidate tags are included:
   ```bash
   previous_stable=$(git describe --tags --abbrev=0 --first-parent \
     --match 'v[0-9]*.[0-9]*.[0-9]*' --exclude '*-*' --exclude '*.rc*' HEAD)
   uv run git-cliff --config cliff.toml --tag vX.Y.Z --strip header \
     "${previous_stable}..HEAD"
   ```
3. Tag and push:
   ```bash
   git tag vX.Y.Z
   git push origin vX.Y.Z
   ```
4. The `release.yml` workflow reruns CI, publishes the versioned backend and
   frontend images, and creates the GitHub release. Stable tags also publish
   `latest`, create `release/vX.Y.Z`, and update `CHANGELOG.md` on `main`.
5. For stable tags, `docs.yml` deploys the versioned MkDocs site and moves the
   `latest` alias. Pushes to `main` update the `dev` documentation version.

Pre-release tags (for example, `v1.0.0-rc1`) are marked as prereleases and do
not update `latest`, create a stable release branch, update `CHANGELOG.md`, or
deploy versioned documentation.

## Local Changelog Preview

```bash
uv sync --group docs

# Preview changes since the most recent tag (the prerelease behavior)
uv run git-cliff --config cliff.toml --latest --strip header

# Generate the complete changelog for a specific version without editing it by hand
uv run git-cliff --config cliff.toml --tag vX.Y.Z --output CHANGELOG.md
```
